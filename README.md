# docstore — 文档存储与数组字段多键索引

一个**不依赖任何数据库**、用纯 Python 写的文档存储，重点解决商品规格数组上的
索引与查询问题。存储层、索引、查询规划器、HTTP 服务全部自己实现，只用标准库。

> 事故背景：运营要查“红色 **且** XL **且** 有货”的规格，线上一条查询
> `{"specs.color":"red","specs.size":"XL","specs.stock":{"$gt":0}}` 却返回了
> “红色 S 码 + 另一个颜色 XL 码”的商品。这个写法在语义上是
> “有一个元素是红的，有一个元素是 XL 的，有一个元素有货”（可以是不同元素）。
> 建了索引之后更慢，是因为多键索引只能安全地用一个条件收窄扫描范围。

本项目把这个歧义**显式化**，两种语义都支持、写法上截然不同、结果可以和全表扫描逐条核对。

---

## 快速开始

```bash
# 1) 生成 30 万商品并写盘（约 1 分钟，含建索引与逐条核对）
python3 -m docstore.bench --count 300000 --out data/catalog

# 2) 打开页面
python3 -m docstore.server --data data/catalog --port 8765
#   浏览器打开 http://127.0.0.1:8765/

# 3) 测试
python3 -m pytest -q
```

`data/catalog/bench.json` 是机器可读报告，`data/catalog/BENCH.md` 是本次运行的
人类可读报告（由 bench 自动生成）。

## 核心设计

### 1. 两种数组语义，写法上必须区分

| 语义 | 写法 | 含义 |
|---|---|---|
| **同一元素** | `{"specs": {"$elemMatch": {...}}}` | 存在 **一个** 规格元素同时满足全部条件 |
| **不同元素各自满足** | `{"$some": {"specs.color": "red", "specs.size": "XL"}}` | 每个条件都 **有某个** 元素满足，可以是不同元素 |
| 隐式扇出（旧写法） | `{"specs.color": "red", "specs.size": "XL"}` | 等价于 `$some`，是想表达“不同元素”时的旧写法 |
| **每个元素都满足** | `{"$every": {"specs.size": {"$ne": "XXS"}}}` | 所有元素都满足；空数组/缺字段为真（文档化） |

运营那条查询的正确写法：

```json
{"specs": {"$elemMatch": {"color": "red", "size": "XL", "stock": {"$gt": 0}}}}
```

`$elemMatch` 和外层的 `$some`/旧写法结果不同——这正是线上 bug 的根因。页面上三条
预设按钮可以一键对比。

**歧义防护**：在顶层写裸算子（如 `{"$eq": ...}`、`{"$gt": ...}`）会被拒绝，并提示
去用 `$elemMatch` 或 `$some`，避免再有“看起来一样、含义不同”的隐式行为。

### 2. 多键索引：一个元素一条索引项

数组字段建索引时，每个数组元素各进入一条索引项：

```
{"_id": 1, "specs": [ {"color":"red","size":"S"}, {"color":"blue","size":"XL"} ]}
索引 specs[].color  →  条目 ("red",) 与 ("blue",)   （每个元素各一条）
```

- **空数组**：产生一条 `[]` 键（是“存在”，所以 `$eq: []`、`$exists: true` 都能走索引）。
- **缺字段**：产生 `<missing>` 键（与 `null` 不同；`$exists` 可区分）。
- **重复元素**：相同值合并成一条 posting（文档去重），但每个不同的元素值各占一条。
- **索引随数据增删**：`array_push` / `array_pop` / 按下标更新 / 整数组替换 / 删文档，
  都会计算“新键集合 - 旧键集合”，只增删差异部分，不会全量重建。

### 3. 复合索引与并行数组

- **同一数组元素上的复合索引**：用 `align="specs"` 声明
  ```python
  col.create_index(["specs[].color", "specs[].size", "specs[].stock"], align="specs")
  ```
  每个数组元素生成一条 `(color, size, stock)` 键，条目总数等于元素总数，**不会爆炸**。
  这才是让运营那条 `$elemMatch` 查询从 O(N) 变成只扫命中集合的关键。

- **两个不同数组字段的复合索引直接拒绝**：`tags` 与 `specs` 都是数组时建复合索引会报
  `PARALLEL_ARRAYS`，因为需要两个集合的笛卡尔积（10×10 = 每文档 100 条）。
  替代方案：两个单字段多键索引 + 索引交集（planner 会自动使用）。
  如果数据在没有声明 `[]` 的情况下实际是数组，写入时也会被拒绝，并且**原子回滚**，不留脏数据。

### 4. 多键索引上的范围上下界：什么时候能合并

多键索引下**一个文档拥有多条索引项**，所以判定“同一元素”是能否合并的关键：

| 情形 | 是否合并区间 | 原因 |
|---|---|---|
| 非多键索引上的 `$gt` + `$lt` | ✅ 合并 | 一个文档一个键，两个界描述同一个值 |
| **同一个** `$elemMatch` 内的上下界 | ✅ 合并 | 必须是同一个元素，合并安全 |
| 同一个条件对象里的 `$gt` + `$lt`（`{"price":{"$gt":10,"$lt":20}}`） | ✅ 合并 | 文档化：一个条件对象 = 同一个元素 |
| `$and` 里两个独立条件 `$gt` / `$lt` | ❌ **分别扫描后求并** | `[1, 30]` 满足“有元素>10”且“有元素<20”，但没有元素落在 (10,20) |
| 复合索引里不同子句、独立元素语义 | ❌ 只用首子句，其余 residual | 对齐键不存在时合并会漏 |

**安全原则**：宁可多扫，也不能漏。不允许合并时，planner 会分别扫描各区间再求并集，
最终仍由匹配器逐条确认。测试里直接构造了 `[1, 30]` 这种文档，验证“合并会漏、求并不会”。

### 5. 两个数组字段共用一个复合索引时的执行

`align` 索引在**独立元素**语义下（`$some` / `$and` 里的独立条件）不能用一条键同时
表达两个子句，于是 planner 只用首个能确定作用域的子句收窄，其余留给匹配器，
或者在多个单字段索引上做**索引交集**（结果精确，已验证交集 = 全表扫描结果）。

### 6. 边角行为（全部有测试）

| 场景 | 行为 |
|---|---|
| 数组字段排序 | 升序取**最小**元素，降序取**最大**元素；索引顺序与内存排序结果逐条一致（含 `_id` 决胜） |
| 缺字段排序 | 排在最前；空数组按数组序（在标量之后） |
| 唯一索引落在数组 | 拒绝：文档该路径是数组时报 `MULTIKEY_UNIQUE_UNSUPPORTED`（逐元素唯一几乎不是本意） |
| 唯一索引重复 | `DUPLICATE_KEY`，写入原子回滚 |
| 按下标更新 `specs[2].stock` | 只改该元素；越界报错**绝不追加**；作用在非数组上报错 |
| 非下标写穿过数组 `specs.stock` | 拒绝，提示用下标写法 |
| `$ne` / `$nin` 作用于数组 | 集合级：没有任何元素等于该值才匹配（缺字段也匹配） |
| `$every` 空数组/缺字段 | 真（文档化） |

### 7. 查询计划

`explain` 输出说明：

- 用了哪个索引、扫描了哪些键区间（含上下界开闭）；
- 每条谓词是否被用作键界，还是留给匹配器（residual）；
- **是否合并区间，以及为什么**（同一个 `$elemMatch` 元素 / 非多键 / 独立见证求并）；
- 扫描条数：`index_keys_examined`、`index_postings_read`、`candidates`、`documents_fetched`、
  `documents_matched`、`elapsed_ms`；
- **为什么不能只用索引返回（covering）**：多键索引一个文档对应多键、无法由键还原字段值；
  查询/投影引用了索引外字段；仍有 residual 谓词；没有投影等，逐条列出。

### 8. 存储层（自己实现）

```
data.log
  magic "DCS1\0"
  记录*: [u32 长度][u32 CRC32][u8 类型][payload JSON]
        类型 1 = put，类型 2 = delete
manifest.json
  {"format":1, "collection":..., "indexes":[...], "records":n}
```

- 追加写 + 每条记录 `fsync`，崩溃后按 CRC 回放；**尾部半条记录**会被截断，不影响前面的数据。
- 中间记录损坏时，回放到损坏处为止（不会返回错乱数据）。
- `compact()` 重写只含存活文档的日志。
- 索引定义与构建状态写入 manifest，重启后自动重建。
- **索引快照**：`idx/*.idx` 保存每个索引的键与 posting，并记录它对应的日志偏移量。
  重启时先读快照，再只回放偏移量之后的新记录；快照缺失/损坏/偏移越界则自动全量重建。
  快照只影响启动速度，不影响正确性（`test_storage.py` 覆盖了回放与损坏回退）。

## 目录结构

```
docstore/
  values.py      值排序与类型编码（缺失 < null < NaN < 数字 < 字符串 < 布尔 < 对象 < 数组）
  paths.py       点路径、索引子句语法（specs[].color）、遍历、下标更新路径
  storage.py     追加日志存储、CRC、崩溃恢复、压缩
  index.py       多键索引：逐元素建项、对齐复合索引、唯一/稀疏、增量维护
  query.py       查询解析、两种数组语义、参考匹配器（唯一真值来源）
  planner.py     选索引、键区间构造、区间合并/求并的安全规则、排序、covering 分析
  collection.py  文档 + 索引 + 读写 + 查询 的组合
  generator.py   确定性商品数据生成（长短不一、空数组、缺字段、类型混用、陷阱文档）
  bench.py       30 万级基准：全表 vs 索引逐条核对、扫描条数与耗时
  server.py      标准库 HTTP 服务
  ui.html        单页界面：写查询、看结果、看计划、看某个文档的索引条目
tests/           81 个测试，覆盖上述每一条行为
```

## UI 功能

- 写查询、看结果（命中的规格行高亮）；
- 看计划（模式、索引、键区间、是否合并及原因、计数、covering 阻断项、语义说明）；
- 看某个文档在**每个索引里占了哪些条目**（点结果里的 `_id`）；
- 建/删索引，统计页可一键做索引一致性校验（与重建结果对比）。

## 一致性保证

**索引只挑选候选，匹配器决定真值。** `find(..., force_scan=True)` 与走索引的 `find`
使用同一个匹配器，因此两者结果必须逐条相等。基准脚本对每个查询都做这件事，
不一致即以非零退出码失败。
